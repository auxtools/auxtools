# Saving the cache across `||=` and `&&=` values

`place ||= value` and `place &&= value` read the place, test it, and only then evaluate the value
and write the place. When the place is a field or a list element, the test leaves its object in the
cache, which evaluating the value can overwrite before the write runs. DreamMaker decides from the
source, rather than from the generated bytecode, whether to save the cache across the value.

## Plain chains

dmasm saves the cache across the value with `PushCache` and `PopCache` in the same cases DreamMaker
does. For a list element, it also saves the key with `PushCacheKey` and `PopCacheKey`.

The cache is saved when the source uses the cache inside the value:

- a global call,
- a list index, or
- a subexpression removed by constant folding (DreamMaker decides before folding, so a folded
  subexpression still counts).

A field access or a receiver call on the place also requires saving the cache. `::` causes this,
whereas static and const reads through `.` and through `global.x` do not. The compiler tracks this
case with `global_field`. A list element's key is also saved when the value changes the key.

The place is emitted again for the write unless it was already in the cache before the test, and
the value does not reuse field chains loaded by the test. An explicit `src.x` does not reuse a
cache loaded by a bare `x`. This applies to both the test and the write, so both read the place in
the same way.

## Safe chains

On a safe chain such as `a?.b.c ||= v`, the test leaves the object holding the last variable in the
cache. DreamMaker does not preserve that cache when the value modifies it. Instead, it writes the
place through the entire chain again starting from whatever object the cache then holds, so
`a?.b.c ||= x.c` writes `a.b.b.c` or fails on `null`.

dmasm diverges from DreamMaker here on purpose. When the value modifies the cache, dmasm saves the
cache around the value (and the key if the value changes that too), then writes only the last
variable from the saved cache, which is the variable the test read. Without saving the cache, the
write would go to whatever object the value left in the cache: for instance,
`items?[1]:owner:owner &&= x.owner` would write to the wrong object's `owner`, or `||=` would fail
with `"Cannot modify null.owner"`. dmasm reports this divergence with the `ByondSafeLogicalWrite`
warning.

While the plain-chain rule reproduces DreamMaker's bytecode, code that depends on DreamMaker
writing `a.b.b.c` behaves differently under dmasm, and `ByondSafeLogicalWrite` flags it.

## Applies to

- `dmasm/compiler/src/compiler/statements.rs`: `keep_cache_across_value`, `keep_tested_place`,
  `emit_safe_chain_write`, `emit_safe_logical_assign`, and the `||=` and `&&=` arm of
  `emit_expr_statement_inner`
- `dmasm/compiler/src/compiler.rs`: `global_field` flag on `Compiler`
- `dmasm/compiler/src/compiler/known_bugs.rs`: `safe_logical_write`
